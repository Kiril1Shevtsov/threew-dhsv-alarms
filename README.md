# DHSV Alarms · 3W

[**Full English documentation**](README.en.md) · Русская версия

Воспроизводимое исследование настройки событийных тревог по данным нефтяных скважин **Petrobras 3W**. Задача — обнаруживать размеченные события **незапланированного закрытия DHSV** и оценивать не только качество отдельных окон, но и нагрузку от ложных тревог.

В репозитории собраны модели, сохранённые прогнозы, расчёт метрик и небольшой интерфейс командной строки для обработки записи Parquet. Это самостоятельный исследовательский проект Кирилла Шевцова и Данилы Литвинова, не официальный продукт Petrobras.

## Основной результат

На выборке разработки из **45 записей, 13 скважин и 22 DHSV-событий** событийная настройка порога HistGradientBoosting уменьшила число ложных эпизодов с **55 до 3**, сохранив **20 из 22** обнаружений в течение пяти минут после размеченного начала события.

| Вариант HGB | Обнаружено за ≤300 с | Без ложных эпизодов во всей записи | Ложных эпизодов | Эпизодов в сутки |
|---|---:|---:|---:|---:|
| Порог 0,5 | 20/22 | 16/22 | 55 | 10,85 |
| Событийный подбор порога | 20/22 | 18/22 | 3 | 0,59 |

Знаменатель нормального режима — **121,675 часа**. Порог выбирается внутри обучающих скважин; скважина внешней проверки исключена и из обучения, и из настройки. Эти записи использовались при разработке подхода: цифры характеризуют исследованный протокол, а не универсальное преимущество над другими решениями.

### Дополнительная проверка

Зафиксированные модели проверены на **15 других скважинах**, содержащих нормальные участки и отказы классов 5, 7 и 9. Для HGB с порогом 0,999:

- **0 ложных эпизодов** на **52,221 часа** размеченной нормы;
- **2 из 15** записей дали DHSV-сигнал во время другого отказа;
- состав этого набора: **0 DHSV-событий**. Поэтому он оценивает ложные тревоги и специфичность диагноза; показатель 20/22 относится к выборке разработки выше.

Нормальные участки здесь взяты из записей с отказами. Дополнительная выборка ограничена файлами меньше 1 МБ, по одному на скважину, выбранными по минимальному Git blob SHA. Эти правила отбора важны при сравнении с другими экспериментами. Ноль наблюдавшихся ложных эпизодов не означает нулевой риск в эксплуатации.

## Быстрый старт

Python 3.12. Рекомендуется отдельное виртуальное окружение:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
python scripts/check_results.py
```

Последняя команда пересчитывает 930 сочетаний «запись — модель — политика тревоги» по включённым прогнозам. Она не требует сети и не обучает модели.

### Прогноз для записи

```bash
python scripts/download_data.py
python scripts/check_data.py
python scripts/predict.py raw/dataset/5/WELL-00015_20170620122925.parquet --output predictions.csv
```

Результат содержит время, оценку модели, порог и подтверждённую тревогу. По умолчанию используются HGB и событийный порог. Другие варианты:

```bash
python scripts/predict.py path/to/record.parquet --model calibrated_RF --policy window_q99 --output predictions.csv
```

Ожидается хронологический индекс с частотой 1 Гц и шесть датчиков: `P-PDG`, `P-TPT`, `T-TPT`, `P-MON-CKP`, `T-JUS-CKP`, `QGL`. Первый час используется для нормировки; прогноз начинается после него. `score` — оценка классификатора, **не калиброванная вероятность физического отказа**.

### Новое обучение

```bash
python scripts/train.py --output runs/hgb
```

Модели Random Forest поставляются готовыми: их прогнозы и событийные метрики можно воспроизвести, но отдельного скрипта повторного обучения RF в этом репозитории нет.

Скрипт повторно обучает HGB во внешнем leave-one-well-out цикле и выбирает пороги по внутренней трёхчастной групповой проверке. Он использует включённую матрицу причинных признаков, а результаты пишет отдельно от опубликованных таблиц. Полный прогон существенно дольше проверки сохранённых прогнозов. При подготовке репозитория этот скрипт повторно выполнил полный цикл HGB: событийные итоги совпали с опубликованными таблицами. [Лог полного цикла](results/hgb_training.log).

## Как устроена тревога

1. Из шести датчиков строятся признаки по последним 180 секундам, шаг 15 секунд.
2. Для нормированного варианта используется медиана и масштаб первого часа без меток.
3. Классификатор выдаёт числовую оценку.
4. Тревога подтверждается после трёх последовательных превышений порога.
5. Оцениваются эпизоды тревоги, доля нормального времени под тревогой и задержка обнаружения. Это разные характеристики; одной недостаточно.

Событийный порог выбирается на сетке с ограничениями на ложные эпизоды и долю времени под тревогой. Это эмпирические ограничения при настройке, а не гарантии для будущих данных.

## Область применения

Этот код предназначен для исследования и сравнения методов на исторических данных. Он не управляет оборудованием, не заменяет системы безопасности и не подтверждает промышленную готовность. Результаты не следует напрямую сравнивать с числами другого benchmark без согласования данных, разбиений и определения тревоги.

Нас интересуют полезные продолжения: другие виды отказов, согласованный benchmark, устойчивость к изменениям датчиков и совместная оценка стоимости пропусков и ложных тревог.

## English summary

This independent research project studies event-level DHSV alarms on Petrobras 3W. On the **development set** (45 records, 13 wells, 22 DHSV events), nested well-grouped HGB threshold selection reduced false alarm episodes from 55 to 3 while retaining 20/22 detections within 300 seconds **after** labelled onset. Clean detection additionally requires no false alarm episodes anywhere in the record.

The fixed models were also evaluated on 15 separate wells containing normal intervals and failure classes 5, 7 and 9. At threshold 0.999, HGB produced zero false episodes across 52.221 normal hours, and DHSV signals during other failures in 2 of the 15 records. This set contains zero positive DHSV events; the 20/22 detection result belongs to development.

The repository includes saved models, predictions, event metrics, data provenance and a full nested HGB retraining script. RF models are supplied pre-trained, without an RF retraining script. We welcome work on additional failure types, agreed evaluation protocols and operationally meaningful alarm costs.
